Architecture

tmux and screen wrap a second VT parser around the host terminal. Doubled glyphs, broken keybinds, no image protocol, no GPU path. séance inverts the model: one terminal, one parser, splits and tabs live natively above the grid.

CSI, OSC, DCS: 50 years of wire format

The DEC VT100 (1978) shipped a wire format every modern terminal still implements. Three escape-sequence families share the same ESC (\x1b) prefix and split by introducer.

CSI (ESC [): control

\x1b[31m         SGR       set foreground red
\x1b[2J          ED        erase in display
\x1b[10;5H       CUP       cursor to row 10, col 5
\x1b[?1049h      DECSET    enter alt screen
\x1b[?25l        DECTCEM   hide cursor
\x1b[6n          DSR       report cursor position

OSC (ESC ]): system

\x1b]0;title\x07          OSC 0    window title
\x1b]52;c;<b64>\x07       OSC 52   write clipboard
\x1b]8;;url\x07x\x1b]8;;\x07
                          OSC 8    hyperlink "x"

DCS (ESC P) / APC (ESC _): payloads

\x1bPq...\x1b\\           DCS Sixel     pixel image
\x1bP+q544e...\x1b\\      XTGETTCAP     query terminfo cap
\x1b_Gf=100,a=T;<b64>\x1b\\
                          APC Kitty     graphics protocol

PTY and VT

A single byte stream traces the whole stack. Watch \x1b[31mhello\x1b[0m world walk in.

PTY: kernel pseudo-terminal

Two file descriptors that pretend to be a serial line. The shell sees the slave as /dev/pts/N: line discipline, winsize, SIGWINCH on resize. séance owns the master, reads raw output, writes user keys.

portable-pty spawns the pair. An IO thread bridges the master fd to the parser.

VT: libghostty-vt

State machine. Bytes in, ops out. Ghostty's parser, exposed via FFI. No second parser to maintain, no drift from upstream as new quirks land. 

let mut vt = VtTerminal::new(opts)?;
vt.vt_write(bytes);
let snap = render_state.update(&vt)?;
for row in snap.rows() { /* … */ }

The renderer: shape, raster, atlas, GPU

The grid is a logical model. Turning it into pixels takes four stages, each backed by a focused crate. Trace "fi =>" through the pipeline.

Shape (cosmic-text + rustybuzz)

Run of styled text becomes glyph IDs and offsets. Ligatures (=>), ZWJ chains, regional flag pairs, and combining marks collapse multiple cells onto one or more glyph instances. 

buf.set_text(
    &mut fs, text, &attrs,
    Shaping::Advanced, None,
);
buf.shape_until_scroll(&mut fs, false);
// → glyph_id, x_advance per run

Rasterize (swash)

Glyph ID becomes a pixel bitmap. Mono for plain glyphs, RGBA for COLR / SVG colour fonts. Cached per CacheKey (font, glyph, size, weight, flags). 

let img = swash.get_image(&mut fs, key);
// → img.data, img.placement

Atlas (etagere)

Bitmaps pack into one big GPU texture. Two planes: 2048×2048 R8 for mono, 1024×1024 RGBA for colour. Each glyph gets a sub-rect; misses fall back to LRU eviction. 

let slot = atlas.allocate(
    Size::new(w, h),
)?;
copy_bitmap(&mut tex, slot, &bitmap);
// → slot.rectangle in atlas

Upload + draw (wgpu)

Dirty rects pushed to the GPU. One render pass, three pipelines: bg_color (fullscreen quad), cell_bg (per-cell rectangles), cell_text (instanced quads sampling the atlas). Runs on Metal, Vulkan, DX12. 

queue.write_texture(
    view, &bytes, layout, extent,
);
// frag: textureSample(atlas, uv)

What shaping actually does

Shaping turns Unicode codepoints into glyphs. The mapping is almost never 1:1. rustybuzz (wrapped by cosmic-text) walks the font's OpenType tables: GSUB substitutes glyph runs (ligatures, contextual alternates, joining forms), GPOS positions them (kerning, mark attachment, cursive joining). The output is a list of glyph IDs with x_advance values plus a cluster index that maps each glyph back to its source codepoints.

Four cases that come up constantly in a terminal:

1. Typographic ligature

GSUB · liga

The font's liga table replaces f + i with one ligature glyph. Two grid cells still hold the run; the renderer anchors the wide glyph at the leftmost cell.

2. Programming ligature

GSUB · calt

JetBrains Mono and Fira Code define calt rules that swap = + > for an arrow glyph, but only in code-like contexts. Same 2 → 1 collapse, different OpenType table.

3. Combining mark

GSUB · ccmp · GPOS · mark

Two codepoints describe one accented letter. GSUB may swap them for a precomposed é glyph; otherwise GPOS positions the combining acute above the e via mark anchors. One grid cell either way.

4. ZWJ cluster

emoji_zwj_sequences

U+200D ZERO WIDTH JOINER stitches base emoji into a single grapheme. Fonts with the matching emoji_zwj entry render one composite glyph; fonts without fall back to the component sequence (man + laptop side by side).

séance plumbs all four through cosmic-text's Shaping::Advanced. Inside cell_builder, a sorted Vec<CellSlot> maps each glyph cluster's byte offset back to the source grid column. That mapping is what lets a ligature like => (one glyph, two cells) anchor at the leftmost cell, the cursor land on the second cell when navigating, selection span the right column count, and a backspace remove the trailing codepoint without breaking the rest of the cluster. Without it, ligatures would either misalign or have to be suppressed entirely.

What rasterization actually does

Shaping picked the glyphs. Rasterization turns each one into actual pixels. swash reads the glyph's vector outline (Bezier curves stored in the font's TTF/OTF/CFF tables), scales it to the target em-size, and scan-converts it onto a pixel grid. The output is an Image: a contiguous byte buffer plus a Placement describing the bitmap's width, height, and baseline offset.

Four ideas the rasterizer hides behind one method call:

1. Outline to pixel grid

scan-convert

Curves get sampled at the target size. Each pixel records how much of the cell the glyph touched (the alpha coverage). Output: a flat byte buffer plus Placement { width, height, top, left }.

2. Anti-aliasing

u8 coverage per pixel

Cells under the curve (dashed) get partial alpha based on what fraction of the cell the glyph fills. 255 is fully inside, 0 outside, in-between values render the soft edge.

3. Mono vs colour planes

R8 vs RGBA

Plain glyphs need only an alpha channel: one byte per pixel, tinted by the cell foreground. COLR / SVG / bitmap fonts (most emoji, Apple Color, Microsoft Segoe) carry their own colour and need RGBA: four bytes per pixel, sampled directly without tinting. Two atlas planes, two fragment-shader branches.

4. Cache key (per-rasterization memo)

SwashCache

Rasterization is expensive but deterministic. The same glyph at the same size, weight, and flags always yields the same bitmap, so swash memoizes CacheKey → Image. Hits skip the scan-converter entirely; misses populate the cache and forward to the atlas allocator.

From séance's perspective, all four steps collapse into one call: swash.get_image(&mut fs, key). The returned Image goes to etagere, which finds a free rectangle in the right atlas plane (mono or colour). The atlas coordinates ride along with the glyph ID in the cell record, ready for the GPU to sample.

Atlas, up close

Two textures live on the GPU. Each glyph rasterized so far occupies a sub-rectangle. Cells in the grid reference the atlas by (u, v, w, h); the fragment shader samples the right plane based on whether the glyph is mono or colour.

How the GPU samples the atlas

The atlas is a wgpu::Texture: a region of GPU memory formatted as a 2D image, addressable by texture coordinates (u, v) ∈ [0, 1]. To draw a cell with glyph 142, the renderer needs to know which sub-rectangle of that texture holds the glyph's bitmap. That mapping is not on the GPU. It lives in a CPU-side hash table populated when the glyph was first rasterized and packed.

Two phases per frame: CPU translates the cell's glyph ID into atlas coordinates and packs them into an instance buffer. GPU draws one instanced quad per visible glyph, sampling the texture at those coordinates.

CPU: look up, pack, upload

The renderer keeps a hash map of every glyph that has ever been rasterized this session. Per visible cell it does one lookup, normalizes the atlas pixels into texture coordinates, and appends a struct to the per-frame instance buffer. 

let entry = atlas_index.get(&glyph_id)?;
// AtlasEntry { pos: [u32; 2], size: [u32; 2], is_color }

let uv = [
    entry.pos[0] as f32 / ATLAS_SIZE,
    entry.pos[1] as f32 / ATLAS_SIZE,
];
let wh = [
    entry.size[0] as f32 / ATLAS_SIZE,
    entry.size[1] as f32 / ATLAS_SIZE,
];

instances.push(GlyphInstance {
    cell_xy: [col * cell_w, row * cell_h],
    atlas_uv: uv,
    atlas_wh: wh,
    fg_color: cell.fg_rgba(),
});

queue.write_buffer(&inst_buf, 0, cast(&instances));
// one DMA per frame, all glyphs in one buffer

GPU: sample the atlas

The vertex shader spreads each instance into a four-vertex quad at the cell's pixel position and forwards the matching atlas uv. The fragment shader reads the texture once at that uv: a coverage byte for mono glyphs, a full RGBA for colour ones. 

// vertex shader (WGSL)
@vertex fn vs(
    @builtin(vertex_index) vid: u32,
    instance: GlyphInstance,
) -> VsOut {
    let corner = QUAD[vid];        // 0..3
    out.pos = instance.cell_xy
            + corner * cell_size;
    out.uv  = instance.atlas_uv
            + corner * instance.atlas_wh;
    return out;
}

// fragment shader (WGSL)
@fragment fn fs(in: VsOut) -> @location(0) vec4<f32> {
    let cov = textureSample(atlas, samp, in.uv).r;
    return vec4(in.fg.rgb, in.fg.a * cov);
}

The split keeps the GPU's job small: it never decides which glyph to sample, only how to sample a region the CPU has already named. This is the whole point of an atlas. The lookup is constant-time HashMap on CPU, the upload is one buffer write per frame, the draw is one instanced quad per visible cell. Add or remove a glyph from the cache: only the HashMap and the relevant atlas sub-rect change. Texture stays put. No GPU-side branching on glyph identity.

Kitty graphics rendering

The Kitty graphics protocol carries actual bitmaps inside the terminal byte stream: PNG images, video frames, plot output, file-manager previews. séance handles it as a separate render pipeline that runs alongside the text pipeline, sharing the same render pass but with its own shader, bind group, and instance buffer.

Two halves: getting the bytes in (libghostty-vt parses and stores) and getting the pixels out (séance walks placements, uploads textures, draws quads).

Two ways to place an image

The protocol carries the bitmap once, then asks the terminal to place it at one or more grid positions. Two encodings, very different ergonomics.

Direct placement

a=p · explicit row/col

Another APC sequence references the stored image_id and names the target row, column, source sub-rect, and z-layer: 

\x1b_Ga=p,i=1,p=42,c=10,r=3,x=0,y=0\x1b\\
// place image 1, placement_id 42,
//   anchor at row 3, col 10, source (0, 0)

Tied to a fixed grid coord. Simple to render: one entry in the placement registry, one quad on screen. The shell tool owns the positioning logic and has to track scrolling itself.

Virtual placement (Unicode placeholder)

U+10EEEE + 297 diacritics

The shell prints regular cells. Each cell carries the base codepoint U+10EEEE plus up to three combining diacritics from a sorted 297-entry alphabet. The diacritics encode (row, col, image_id_high). The cell's foreground colour carries the low 24 bits of image_id.

The image scrolls with the text because the cells are the text. No placement IDs to track. Each diacritic's index in the 297-entry alphabet is the encoded value (0..296), so a 297×297 grid of cells suffices for any reasonable image.

Per-frame: walk, instance, draw

séance does not own the image storage. libghostty-vt does. Each frame, FrameSource calls into the placement iterator three times, once per z-layer (BelowBg, BelowText, AboveText), and accumulates one ImageInstance per visible placement: 

struct ImageInstance {
    dest_rect: [f32; 4],   // pixel x, y, w, h on screen
    source_uv: [f32; 4],   // u, v, w, h in image texture
}

// vertex shader expands a triangle-strip quad at dest_rect
// fragment shader samples image_tex at source_uv, premultiplies
//   alpha, returns rgba

What shaping makes possible

The shape stage handles long-tail Unicode that breaks naive per-codepoint terminals. Multi-cell ligatures, box-drawing, symbolic icons.

Why FFI Ghostty's parser

A VT parser is not a weekend project. The state machine has to handle CSI, OSC, DCS, APC, the alt screen, scrollback, mouse encodings, Kitty keyboard, DEC modes, and a long tail of terminal-specific quirks accumulated since the VT100. Ghostty has shipped a battle-tested parser; libghostty-vt exposes it via FFI. Writing a second one would mean rebuilding that quirk history, then drifting from upstream as Ghostty fixes new bugs. Same parser, no double-render, no second source of truth.
